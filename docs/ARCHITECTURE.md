# 아키텍처 — 에이전트가 위하고를 직접 조작해 부가세 신고서를 작성한다

## 결론

**Claude Code(헤드리스) + Playwright MCP로 에이전트가 위하고 화면을 직접 조작한다.
자체 엔진은 그 에이전트에게 작업지시서를 주고, 결과를 검증한다.**
에이전트가 한 번 성공한 동작은 레시피로 저장한다. 다음부터는 AI 없이 그대로 재생하고, 재생이 깨진 지점부터만 AI가 이어받는다.

```
           ┌──────────── 작업지시서(무엇을 어떻게 고칠지) ────────────┐
           │                                                          ▼
 [엔진] 정규화·공제판정·독립 재계산·검증            [에이전트] 위하고 조작
   ▲   src/taxauto/                                    Claude Code + Playwright MCP
   │                                                   ├ 레시피 재생(토큰 0, 빠름)
   └──── 위하고에서 내려받은 전표·신고서(대사) ◀────────┤ 실패 지점부터 AI가 직접 조작
                                                       └ 성공하면 레시피 자동 갱신
```

## 왜 이 조합인가 (추천 순위)

| 순위 | 방식 | 점수 | 판단 |
|---|---|---|---|
| **1** | **Claude Code 헤드리스 + Playwright MCP + 레시피 재생 + 검증엔진** | **88** | 에이전트 루프를 직접 만들지 않는다. Claude Code가 업그레이드되면 조작 능력도 같이 오른다. 반복 작업은 레시피 재생이라 비용이 거의 안 든다. 결과는 엔진이 독립적으로 재계산해서 대조한다 |
| 2 | Claude Agent SDK로 자체 앱 | 75 | 제어는 세밀하지만 직접 작성하고 유지할 코드가 많다. 1안이 한계에 닿으면 넘어간다. 스킬·MCP·레시피를 그대로 재사용하므로 갈아타는 비용은 작다 |
| 3 | Computer Use(화면 픽셀 인식) | 60 | UI가 바뀌어도 잘 버티지만 느리고 비싸다. DOM으로 못 읽는 캔버스 그리드에서만 보조로 쓴다 |
| 4 | 매번 Claude에 말로 지시 | 45 | 재현이 안 되고, 감사 추적이 안 되고, 비용이 많이 들고, 무인으로 돌리기 어렵다 |
| 5 | 순수 RPA 스크립트 | 40 | 위하고 화면이 바뀌면 깨지고, AI 발전의 이득을 못 받는다 |

## 신고 1건을 에이전트가 처리하는 흐름

| # | 위하고에서 하는 일 | 주체 | 수준 |
|---|---|---|---|
| 1 | 로그인 확인, 수임처(회사) 전환 | 에이전트 | 구현 가능(첫 로그인·2차인증은 사람이 1회) |
| 2 | 홈택스 자료 수집 실행 | 에이전트 | 구현 가능(위하고에 세무대리인 인증서가 등록돼 있다는 전제) |
| 3 | 매입매출 자동전표 생성 | 에이전트 | 구현 가능 |
| 4 | 전표 목록 엑셀 다운로드 → 엔진 투입 | 에이전트→엔진 | 구현 |
| 5 | 공제판정·검증 → **작업지시서** 생성 | 엔진 | 구현 |
| 6 | 불공제 전환·고정자산 표시·중복 정리 | 에이전트 | **부분 구현**: 그리드가 캔버스 방식이면 엑셀 업로드나 화면 인식으로 처리 |
| 7 | 부가세 신고서 작성(불러오기, 부속서류, 예정고지세액) → 저장 | 에이전트 | 구현 가능 |
| 8 | 신고서 내보내기 → 엔진이 독립 재계산값과 **라인별 대사** | 에이전트→엔진 | 구현 |
| 9 | 전자신고 파일 제작 | 에이전트 | 구현 가능 |
| 10 | 홈택스 제출 | **사람** | 기술적으로는 가능하지만 **의도적으로 막아 둠**(세무대리인 책임) |

8번 대사가 **불일치하면 그 거래처는 "작성완료"로 표시하지 않는다.** 아침 검토 큐로 넘긴다.

## 위하고 화면을 모르는 문제를 푸는 방법: 학습 → 재생 → 자가복구

1. **학습 모드**(첫 1~2회, 세무사 참관): 에이전트가 메뉴를 탐색하면서 `procedures/*.md`(절차서)와 `recipes/*.yaml`(재생 레시피)을 직접 작성한다.
2. **야간 재생**: 레시피를 Playwright로 그대로 재생한다. 토큰이 들지 않고 빠르다.
3. **자가복구**: 화면이 바뀌어 재생이 실패하면 그 단계부터 에이전트가 이어받는다. 성공하면 레시피를 고쳐서 저장한다.

이렇게 하면 AI가 좋아질수록 학습·복구 성공률이 오르고, 같은 일을 반복할수록 비용은 내려간다.

## 안전장치 (여러 겹)

1. **위하고 에이전트 전용 직원계정에서 전자신고 제출 권한을 빼 둔다.** 가장 강력한 장치다. 위하고 권한설정으로 가능한지 확인이 필요하다.
2. **브라우저 프로필에서 URL을 차단한다.** 홈택스 신고 제출 경로를 막는다.
3. **Claude Code PreToolUse 훅**: "제출·일괄삭제·마감취소" 같은 버튼 클릭을 차단하고, 임의 JS 실행 도구는 항상 막는다.
4. **스킬 지시**: 화면이 불확실하면 추측해서 누르지 않는다. 스크린샷을 남기고 다음 거래처로 넘어간다.
5. **엔진 대사**: 에이전트가 입력한 결과를 독립 재계산값과 비교한다. 다르면 완료 처리하지 않는다.

## 실행 위치와 시간

- **사무실 상시가동 Windows PC**를 쓴다(공동인증서·위하고 세션 유지 때문). 작업 스케줄러가 매일 02:00에 실행한다.
- 현실적인 속도: AI가 직접 조작하면 거래처당 수 분~십수 분, 레시피 재생이면 거래처당 1~3분 수준으로 본다(실측 필요).
- 비용: AI가 직접 조작하는 단계는 화면 정보를 많이 읽어서 토큰 소모가 크다. **구독 주간 한도로 거래처 수십 곳을 매일 AI 조작으로 돌리는 건 무리다.** 그래서 레시피 재생 구조가 필수다. 처음 학습할 때만 비싸다.

## AI가 발전해도 버리지 않는 장치

1. 세법 숫자는 데이터로 둔다(`config/law/*.yaml`, 적용기간·근거 포함).
2. 모델명은 설정 한 줄이다(`policy.yaml`).
3. 도구는 MCP 표준이다. 에이전트가 바뀌어도 엔진은 그대로 쓴다.
4. 절차는 Skill과 절차서(Markdown)로 둔다. 모델이 바뀌어도 그대로 읽히고, 에이전트가 학습 노트를 덧붙인다.
5. 레시피는 "AI가 배운 것의 캐시"다. 모델이 좋아지면 학습·복구가 좋아지고, 재생 부분은 비용이 0이다.
6. 사람 결정은 거래처 메모리에 쌓이고, 반복되면 공용 규칙으로 승격된다.
7. 신뢰도 임계값 하나로 자동 반영 범위를 조절한다.
8. (로드맵) 지난 회차 실제 신고서를 정답셋으로 쌓아서, 새 모델·새 규칙의 성능을 숫자로 비교한다.

- 홈택스 최종 제출: 사람이 한다.
